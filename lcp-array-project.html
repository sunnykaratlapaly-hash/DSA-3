Longest common prefix arrays, built from suffix arrays

Sort every suffix of a string and you get a suffix array. Record how many leading characters each suffix shares with the one before it and you get the LCP array. Type a word below and watch both appear.

Suffixes are listed in sorted order. Highlighted characters are the prefix shared with the row above, and their count is the LCP value.

How Kasai's algorithm skips the repeated work

The naive method compares each pair of neighbouring suffixes from the first character. Kasai's method visits suffixes in text order instead. If suffix i shares h characters with its predecessor, then suffix i+1 shares at least h−1 with its own. So h only ever drops by one per step, and the total number of comparisons stays under 2n.

Four substring questions, answered from the two arrays

Once the suffix array and LCP array exist, none of these queries needs to scan the text again.

Pattern search

Binary search the sorted suffixes. Every match sits in one contiguous block of the suffix array.

Longest repeated substring

The largest LCP value is the longest prefix shared by two different suffixes.

Distinct substrings

Total substrings n(n+1)/2, minus the sum of the LCP array, which counts the duplicates.

Longest common substring

Join both texts with a separator, then take the largest LCP between neighbours that come from different texts.

Benchmarks: naive vs Kasai

Both methods produce identical LCP arrays on every run. They differ in time. On random 4-letter text Kasai is a steady 2 to 3 times faster. On a string of one repeated letter, the naive method slows quadratically and Kasai does not, reaching 786 times faster at n = 3200.

Background and goals

Computing the LCP array by brute force takes O(n²) time in the worst case, which is impractical for the large texts used in compression and analytics pipelines. This project builds the suffix array, implements the naive method as a correctness baseline, implements Kasai's linear-time method, and checks that the two agree.

Research this builds on

  • 1993

    Manber and Myers introduced the suffix array as a space-efficient alternative to suffix trees, buildable in O(n log n).

  • 1994

    Burrows and Wheeler described a reversible text transform on sorted rotations, equivalent to a suffix array and the basis of bzip2-style compressors.

  • 2000

    Ferragina and Manzini combined the BWT with suffix arrays to build FM-indexes for compressed full-text search.

  • 2001

    Kasai, Lee, Arimura, Arikawa and Park proposed the linear-time LCP algorithm used here, based on the fact that the match length drops by at most one per step.

  • 2003

    Kärkkäinen and Sanders presented the DC3 (skew) algorithm, building suffix arrays in O(n) time for very large texts.

What was built

  • Suffix array construction
  • Naive O(n²) LCP algorithm as the baseline
  • Kasai's O(n) LCP algorithm, verified against the baseline
  • Pattern search, longest repeated substring, distinct-substring count, longest common substring
  • Benchmarks on random and worst-case text

What it needs to run

  • Any PC or laptop with a dual-core processor and 4 GB RAM (8 GB for larger benchmarks)
  • No GPU, since everything runs on the CPU
  • Python 3.10 or later, standard library only
  • Optional: matplotlib for benchmark charts
  • Windows, Linux or macOS

Conclusion

Kasai's algorithm computes the LCP array in O(n) and matched the O(n²) method on every test. It was up to about 786 times faster on repetitive worst-case text and 2 to 3 times faster on random text. Together the two arrays answer substring queries efficiently with modest memory, which is why they sit underneath BWT-based compressors, duplicate-content detection and genome alignment tools.

Future scope

  • Replace suffix array construction with the O(n) DC3/skew algorithm for genomic and web-scale texts.
  • Add a suffix-tree emulation layer, such as LCP-interval trees, for richer structural queries.
  • Use the toolkit inside a real Burrows-Wheeler compressor and measure compression ratio and speed.
  • Parallelise LCP construction and pattern search for multi-core or distributed processing.
